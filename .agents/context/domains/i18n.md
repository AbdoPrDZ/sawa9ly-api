# Internationalisation

Three languages: **English, French, Arabic**. English is the default and the
reference. Arabic is written right to left, and the whole interface mirrors for
it.

## The language lives on the account, not in the browser

`Setting` key `sawa9ly_locale` (`LOCALE_KEY` in `src/models/setting.py`),
read through `User.locale(db)` and written through `User.set_locale(db, …)`.

**A setting, not a column**, so adding a language is not a schema change and
`create_all` is not involved. That was the deciding factor: the column route would
have meant asking every installation to delete its database.

This has to be server-side for a reason beyond convenience: **the same value
decides the language of that user's Telegram notifications.** A language kept only
in the browser would let the screen and the notifications disagree, and on a
second device the screen would be the one that looks wrong.

So `locale` is returned on `SessionUserOut` and read from the signed-in user by
the dashboard's shell, which is why it is on the login response and not only on
the profile — the shell has to know the language before it renders anything. The
user changes it on the profile page with `PATCH /api/auth/me/profile`, and the
page then calls `session.refresh()`, because the shell reads the language from the
session and would otherwise keep the old one until a reload.

An unrecognised stored value falls back to English rather than raising: a
hand-edited row is a rough edge, not a reason to refuse to send somebody a stock
alert. A `locale` the *API* is sent is a **400**, because that is a request being
refused rather than bad data being read.

## Messages are keyed, never matched on text

`src/i18n.py` holds `Locale` and `Messages`; `Messages.get(key, locale, **fields)`
renders. The English string is **not** an identifier — rewording "Product 5663 is
available" must not orphan the French and Arabic versions of it — so nothing is
found by matching prose.

- **A key missing from a language falls back to English.** A notification that
  fails to build is an outage, and the product went out of stock regardless of
  what the bot says.
- **An unknown key raises**, naming the key. That is a bug in the caller, and an
  English default would hide it.

The dashboard has its own catalogue in `dashboard/src/i18n/catalog/{en,fr,ar}.ts`,
with the same rule mirrored: a missing translation logs and falls back. `fr.ts`
and `ar.ts` are typed as complete `MessageKey` maps, so **forgetting a key is a
compile error** and the runtime fallback is only a floor.

## One event, one notification row per language

`Notification` deliberately holds a single `title` and `body` — its docstring
calls the body "the text that went, verbatim, and it is the audit trail". That is
incompatible with one row for an event whose watchers read different languages:
three texts, one place to keep them.

So `Notifications.product_changed` **groups the watchers by language and creates
one row per language**, each written in the language its readers will receive, and
returns a **list**. `tracking._notify` returns that list, and logs inside
`Notifications` rather than on the row.

Every property that mattered is intact — one row still carries exactly the text
that was sent to that group, `Notification.for_user` still answers "what was I
told", a failed delivery is still retryable alone. What changed is the count. That
is safe because nothing de-duplicates on `Notification`; `latest_for`, the one
method that could have, is **dead code** — defined, never called.

`_watchers_by_locale` orders by `Locale.ALL` rather than by who was found first,
so a run that finds the same watchers writes its rows in the same order every time.

## Numbers keep Western digits, in every language

`Locale.numbers(value, locale)` changes only the thousands separator: a comma
everywhere except French, which gets a **no-break space (U+00A0)**.

Two deliberate non-choices here, both about not making the reader do extra work:

- **Not U+202F** (the narrow no-break space current French typography prefers).
  That is the right choice in a browser with a modern font and the wrong one in a
  Telegram message, where a client without the glyph shows a box. A message about
  a price has to be readable everywhere.
- **Not Arabic-Indic digits**, though Arabic locales may write ١٦٬٠٠٠. These
  prices are compared by eye against a price on the site, and a reader who has to
  re-parse a price in different digits before acting on it has been slowed down by
  the localisation.

## Arabic mirrors the layout, so the CSS is logical

`I18nProvider` sets `lang` and `dir` on `<html>`. `dir="rtl"` is the whole
mirroring mechanism, which only works because the CSS was written for it:

- **Tailwind's logical utilities**, not the physical ones: `ms-`/`me-`, `ps-`/`pe-`,
  `start-`/`end-`, `text-start`/`text-end`, `border-s`/`border-e`. A `ml-2` here
  would leave every offset on the wrong side in Arabic.
- **`.menu` uses `inset-inline-end`, not `right`**, and `.data-table th` uses
  `text-align: start`.
- **The closed drawer picks its off-screen transform from `direction`.** "Off
  screen" is the *opposite* side in each direction, so a closed rail has to go
  further left in LTR and further right in RTL — that is not something an `rtl:`
  variant can express without fighting the base utility.

The provider sits **above** the signed-in check, because the login screen is
translated too and has no user to read a language from. Before sign-in it falls
back to a language remembered in `localStorage` (`sawa9ly.dashboard.locale`) —
**only** for that screen. It is never sent to the server, so signing in from a
shared or new device cannot change the account's language.

## What is deliberately not translated

- **CLI commands** (`python main.py catalogue save <id>`) are shown as `<code>`
  beside a translated lead-in. They are things to be copied and are the same in
  every language.
- **"Start Bot" and "Open in Web"** in the Telegram panel are labels printed on a
  page this project does not control. Translating them would point at a button
  that is not there.
- **The product title** in a notification is the site's own wording.
- **Operator errors** from `Telegram` (`No bot token. Set …`) are for the person
  running the CLI, not for a user reading a chat.

## Adding a language

1. Add the code to `Locale.ALL` in `src/i18n.py` and to `Locale`/`RTL_LOCALES` in
   `dashboard/src/i18n/translations.ts`, and to the `Locale` union in
   `dashboard/src/api/types.ts`.
2. Add a `catalog/<code>.ts` — the compiler lists every key it is missing.
3. Translate the `CATALOGUE` in `src/i18n.py`. `Locale.RTL` is the only thing that
   decides the mirroring, so a new right-to-left language is a one-line change
   provided the CSS has no physical properties left in it.
